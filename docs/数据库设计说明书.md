## 2. 存储方案概述

### 2.1 选型理由
- 单机离线应用，数据仅供本机单用户使用，无需网络与并发写服务，SQLite 零配置、单文件、免安装，天然契合。
- 支持事务、外键、索引与 WAL 增量写，足以支撑日频次、低并发的工作台场景。
- 数据文件随应用目录即可整体拷贝，便于备份与便携迁移。

### 2.2 文件位置
- 默认目录：`app.getPath('userData')/data`，Windows 下即 `%APPDATA%/Workbench/data`。
- 数据库文件：`workbench.db`；WAL 模式启用后同目录下还会出现 `workbench.db-wal`（预写日志）与 `workbench.db-shm`（共享内存索引）两个临时文件。
- 自定义位置（应用内更改）：设置页「更改位置」经 `app:change-storage` 把数据库迁移到 `<所选文件夹>/Workbench/`，配置写入 `userData/storage.json`（`{ "dataDir": "绝对路径" }`，与数据库分离存放，属目录配置而非业务数据）；迁移时先 `wal_checkpoint(TRUNCATE)` 再复制 `workbench.db` 与 `-wal`/`-shm` 文件，随后热切换重开；原位置文件保留。启动时由 `storageService.init()` 读取该配置并覆盖默认目录。
- 可通过环境变量 `WORKBENCH_DATA_DIR` 重定向 `userData` 根目录（便携模式 / 开发调试，优先级最高，此时忽略 `storage.json` 且禁用应用内更改），见 `src/main/index.ts`。

### 2.3 驱动适配策略
`src/main/db/sqlite-adapter.ts` 通过统一接口屏蔽底层驱动差异：
- 优先加载 `better-sqlite3`（13.0.3，性能最佳，随应用打包）；加载失败（如原生模块 ABI 不匹配）时自动回退到 Node 内置 `node:sqlite` 的 `DatabaseSync`。
- 对外统一暴露三个接口：`SqliteDatabase`（exec / prepare / close）、`SqliteStatement`（run / get / all）、`SqliteRunResult`（changes / lastInsertRowid）。业务层仅依赖该接口，便于替换驱动与单元测试。
- 当前实际驱动名可通过设置页「关于信息」查看（`settingsService.driver()`）。

### 2.4 连接参数
打开数据库后立即执行以下 PRAGMA（两种驱动一致）：

| PRAGMA | 取值 | 作用 |
| --- | --- | --- |
| journal_mode | WAL | 预写日志，提升读写并发与写入性能 |
| synchronous | NORMAL | 兼顾安全与性能的持久化级别 |
| foreign_keys | ON | 启用外键约束，级联删除生效 |

应用退出（`closeDb`）前执行 `PRAGMA wal_checkpoint(TRUNCATE)`，将 WAL 内容合并进主库并收缩日志文件。

## 3. 数据库 ER 关系概览

```text
habits (id PK)
   |-- 1:N --> habit_logs (habit_id FK, ON DELETE CASCADE, UNIQUE(habit_id,date))

asset_accounts (id PK)
   |-- 1:N --> asset_records (account_id FK, ON DELETE CASCADE)

saving_goals (id PK)
   |-- 1:N --> saving_deposits (goal_id FK, ON DELETE CASCADE)

settings      独立键值表（key PK）
schedules     独立（按 date 查询）
todos         独立（按 date 查询）
priorities    独立（按 date 查询）
focus_logs    独立（按 date 查询）
birthdays     独立（生日定义，无外键关联）
moods         独立（每日心情，date 主键，无外键关联）
anniversaries 独立（倒数日/纪念日定义，无外键关联）
```

关系说明：
- `habits` 与 `habit_logs` 为一对多（1:N），每个习惯每天至多一条打卡记录，由 `UNIQUE(habit_id, date)` 保证；删除习惯级联删除其打卡记录。
- `asset_accounts` 与 `asset_records` 为一对多，账户余额随收支记录的新增/编辑/删除在同一事务中联动更新（见 4.12）；删除账户级联删除其全部收支记录。
- `saving_goals` 与 `saving_deposits` 为一对多，目标当前已存金额由存入明细汇总得出；删除目标级联删除其全部存入明细。
- `schedules`、`todos`、`priorities` 无显式外键，通过 `date` 归集到「某一天」，是首页与每日计划页统计口径的数据来源。
- `focus_logs` 记录每日计划页专注计时明细，按 `date` 汇总；`settings` 为全局键值配置。
- `birthdays` 为生日定义表，独立存在、无外键关联；`calendar` 字段区分公历（solar）与农历（lunar），下次生日由 `month`、`day` 结合历法换算得出（农历生日按对应农历年换算为公历，闰月按同号月份、农历三十在 29 天月份回退当月最后一天）。
- `moods` 为每日心情表，以 `date` 作为主键（一天一条），独立存在、无外键关联；写入采用 upsert（`ON CONFLICT(date) DO UPDATE`），供首页「心情打卡」卡片与日历月视图共用。
- `anniversaries` 为倒数日/纪念日定义表，独立存在、无外键关联；`kind` 区分倒数日（countdown，含起始年份 `year`）与纪念日（anniversary，`year` 可空），目标日期由 `year`、`month`、`day` 推算。
- V4 迁移已删除的 5 张历史表（modules、module_records、module_notes、news、reviews）不再参与任何关联，详见 6.5。

## 4. 表结构详细设计

约定：SQLite 为动态类型，索引与约束以声明类型为准。布尔语义统一用 `INTEGER` 的 0/1 表示，TS 侧映射为 `boolean`。时间戳字段默认值均为 `datetime('now','localtime')`，格式为 `YYYY-MM-DD HH:mm:ss`。

### 4.1 settings（应用设置）
用途：存储全局配置的键值对。TS 映射：无独立接口，经 `settingsService` 读写，主要为 `AppSettings.userName`、侧边栏配置 `AppSettings.sidebar`（仅记录可配置功能，固定四项不入库）与外观主题 `AppSettings.theme`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| key | TEXT | PRIMARY KEY | 无 | 配置项名称，如 `userName`、`sidebar`、`theme` |
| value | TEXT | NOT NULL | 无 | 配置项取值（统一以字符串存储；`sidebar` 为功能 id 数组的 JSON 字符串，`theme` 为主题 id 字符串） |

主键：`key`。外键：无。索引：主键隐式唯一索引。

### 4.2 schedules（日程）
用途：一天中带固定时间的安排。TS 映射：`Schedule`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键；TS：id |
| date | TEXT | NOT NULL | 无 | 日期 `YYYY-MM-DD`；TS：date |
| time | TEXT | NOT NULL | 无 | 开始时间 `HH:mm`；TS：time |
| title | TEXT | NOT NULL | 无 | 标题；TS：title |
| description | TEXT | NOT NULL | '' | 描述；TS：description |
| done | INTEGER | NOT NULL | 0 | 是否完成 0/1；TS：done(boolean) |
| sort_order | INTEGER | NOT NULL | 0 | 同日排序序号；TS：sortOrder |
| created_at | TEXT | NOT NULL | datetime('now','localtime') | 创建时间；TS：createdAt |

主键：`id`。外键：无。索引：`idx_schedules_date(date)`。

### 4.3 todos（待办）

主键：`id`。外键：无。索引：`idx_todos_date(date)`。

### 4.4 habits（习惯定义）
用途：需要按天重复打卡的习惯。TS 映射：`Habit`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |

### 4.5 habit_logs（习惯打卡记录）
用途：习惯的每日打卡明细。TS 映射：经 `habitService` 输出 `HabitWithProgress`（count 字段）。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键 |
| habit_id | INTEGER | NOT NULL，REFERENCES habits(id) ON DELETE CASCADE | 无 | 所属习惯；TS：habitId |
| date | TEXT | NOT NULL | 无 | 打卡日期 `YYYY-MM-DD`；TS：date |
| count | INTEGER | NOT NULL | 0 | 当日打卡次数；TS：count |

约束补充：应用层将 `count` 限制在 `[0, target * 3]` 区间（见 `habitService.checkIn`）。

### 4.8 birthdays（生日）
用途：记录需要提醒的生日，支持公历与农历两种历法，供日历页的生日管理与生日提醒使用。TS 映射：`Birthday`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键；TS：id |
| name | TEXT | NOT NULL | 无（空值由应用层回退为「未命名」） | 姓名/称呼；TS：name |
| calendar | TEXT | NOT NULL | 'solar' | 历法：solar=公历 / lunar=农历；TS：calendar |
| month | INTEGER | NOT NULL | 无 | 月份 1-12；TS：month |
| day | INTEGER | NOT NULL | 无 | 公历 1-31 / 农历 1-30；TS：day |
| remind_days | INTEGER | NOT NULL | 0 | 提前提醒天数 0-60；TS：remindDays |
| note | TEXT | NOT NULL | '' | 备注；TS：note |
| created_at | TEXT | NOT NULL | datetime('now','localtime') | 创建时间；TS：createdAt |

主键：`id`。外键：无（独立表，不与其他表关联）。索引：无显式索引（数据量小，列表直接全量读取）。
约束补充：写入前由 `birthdayService.save` 统一 normalize——`month` 限定 1-12；公历 `day` 按当月天数校验（闰年 2 月允许 29）；农历 `day` 限定 1-30；`remind_days` 限定 0-60；`name` 为空时回退为「未命名」。

### 4.9 moods（每日心情）
用途：记录每天的 5 档心情，供首页「心情打卡」卡片与日历月视图展示、回看与补记（首页据此计算连续打卡天数）。TS 映射：`MoodRecord`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| date | TEXT | PRIMARY KEY | 无 | 日期 `YYYY-MM-DD`，一天一条；TS：date |
| mood | INTEGER | NOT NULL | 无 | 心情等级 1-5（1 糟糕 / 2 低落 / 3 一般 / 4 不错 / 5 开心）；TS：mood |
| updated_at | TEXT | NOT NULL | datetime('now','localtime') | 更新时间，写入时刷新；TS：updatedAt |

主键：`date`。外键：无（独立表，不与其他表关联）。索引：主键隐式唯一索引。
约束补充：心情等级在应用层收敛到 1-5（非法值回退为 3）；写入使用 upsert（`INSERT ... ON CONFLICT(date) DO UPDATE`），清除某日记录时由服务层执行 `DELETE`（`mood` 传入 `null`）。

| day | INTEGER | NOT NULL | 无 | 日 1-31；TS：day |

### 4.11 asset_accounts（资产平台账户）
用途：资产模块的平台账户定义，余额随收支记录联动更新。TS 映射：`AssetAccount`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键；TS：id |
| platform | TEXT | NOT NULL | 'other' | 平台 key：alipay/wechat/jd/icbc/ccb/abc/boc/cmb/bocom/psbc/cash/other 共 12 个，未知值回退 `other`；TS：platform |
| name | TEXT | NOT NULL | 无 | 账户名称；TS：name |
| balance | REAL | NOT NULL | 0 | 当前余额（元），保留两位小数；TS：balance |
| note | TEXT | NOT NULL | '' | 备注；TS：note |
| sort_order | INTEGER | NOT NULL | 0 | 排序序号，新增时取当前最大值 +1；TS：sortOrder |
| created_at | TEXT | NOT NULL | datetime('now','localtime') | 创建时间；TS：createdAt |
| updated_at | TEXT | NOT NULL | datetime('now','localtime') | 更新时间，编辑账户或余额联动时显式改写；TS：updatedAt |

主键：`id`。外键：无。索引：无显式索引（列表按 `sort_order, id` 排序，数据量小）。
约束补充：`balance` 的写入统一经 `ROUND(..., 2)` 处理（新增/编辑账户时由应用层四舍五入到分，收支联动时由 SQL `ROUND(balance + ?, 2)` 完成），防止浮点误差累积。

### 4.12 asset_records（收支记录）
用途：各账户的收支明细，与账户余额在同一事务中联动。TS 映射：`AssetRecord`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键；TS：id |
| account_id | INTEGER | NOT NULL，REFERENCES asset_accounts(id) ON DELETE CASCADE | 无 | 所属账户；TS：accountId |
| kind | TEXT | NOT NULL | 'expense' | 收支类型：income=收入 / expense=支出；TS：kind |
| category | TEXT | NOT NULL | '其他' | 分类（如餐饮、交通、工资等）；TS：category |
| amount | REAL | NOT NULL | 0 | 金额（元），正数、保留两位小数；TS：amount |
| date | TEXT | NOT NULL | 无 | 收支日期 `YYYY-MM-DD`；TS：date |
| note | TEXT | NOT NULL | '' | 备注；TS：note |
| created_at | TEXT | NOT NULL | datetime('now','localtime') | 创建时间；TS：createdAt |

主键：`id`。外键：`account_id → asset_accounts(id)`，级联删除。索引：`idx_asset_records_account(account_id)`、`idx_asset_records_date(date)`。
余额联动（`assetService`）：记录的新增/编辑/删除与 `asset_accounts.balance` 更新在同一事务（`BEGIN`/`COMMIT`/`ROLLBACK`）中完成——新增按 `income +amount`、`expense -amount` 入账；编辑先按旧记录反向冲正、再按新值入账；删除按原记录冲正。余额更新使用 `ROUND(balance + ?, 2)` 防浮点误差。总资产趋势的口径为：当前总余额减去「今天之后」全部记录的净额，再自今天向前按窗口内每日收支逐日回推。

### 4.13 saving_goals（攒钱目标）
用途：攒钱计划与「想买」清单的目标定义。TS 映射：`SavingGoal`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键；TS：id |
| kind | TEXT | NOT NULL | 'plan' | 类型：plan=攒钱计划 / wish=想买；TS：kind |
| name | TEXT | NOT NULL | 无 | 目标名称；TS：name |
| target | REAL | NOT NULL | 0 | 目标金额（元）；TS：target |

主键：`id`。外键：无。索引：无显式索引（数据量小，列表直接全量读取）。
约束补充：当前已存金额不冗余存储，由 `saving_deposits` 汇总（`SUM(amount)`）得出；`kind`、`period` 取值范围由应用层保证。

用途：攒钱目标的每笔存入记录。TS 映射：`SavingDeposit`。

| goal_id | INTEGER | NOT NULL，REFERENCES saving_goals(id) ON DELETE CASCADE | 无 | 所属目标；TS：goalId |
| amount | REAL | NOT NULL | 0 | 存入金额（元）；TS：amount |

主键：`id`。外键：`goal_id → saving_goals(id)`，级联删除。索引：`idx_saving_deposits_goal(goal_id)`。

## 5. 索引与查询优化

显式索引共 8 个，均服务于「按日期过滤」或「按外键聚合」的查询；其余为各表主键与唯一约束的隐式索引。

| 索引名 | 表 | 列 | 服务的查询场景（对应服务方法） |
| --- | --- | --- | --- |
| idx_schedules_date | schedules | date | `scheduleService.list`、`statsService.taskCount`（`WHERE date = ?`） |
| idx_todos_date | todos | date | `todoService.list`、`statsService.taskCount`（`WHERE date = ?`） |
| idx_priorities_date | priorities | date | `priorityService.list`、`statsService.taskCount`（`WHERE date = ?`） |
| idx_habit_logs_date | habit_logs | date | `habitService.countsByDate`（`WHERE date = ?`） |
| idx_focus_logs_date | focus_logs | date | `focusService.todayMinutes`、`statsService.focusMinutes`（`WHERE date = ?`） |
| idx_asset_records_account | asset_records | account_id | `assetService.records` 按账户过滤（`WHERE account_id = ?`） |
| idx_asset_records_date | asset_records | date | `assetService.summary` / `assetService.trend` 的日期区间聚合（`WHERE date >= ? AND date <= ?`） |
| idx_saving_deposits_goal | saving_deposits | goal_id | `savingsService` 汇总各目标已存金额（`WHERE goal_id = ?`） |

其他可利用的隐式索引：
- `habit_logs` 的 `UNIQUE(habit_id, date)` 复合唯一索引，可用于 `WHERE habit_id = ?`（`habitService.checkedDates`）及 `habit_id + date` 等值定位。
- `statsService.habitCount` / `habitCompletionCount` 以 `habits` 为主表 `LEFT JOIN habit_logs ON habit_id = ? AND date = ?`，习惯表数据量小，主要开销在 habit_logs 的复合唯一索引命中。

优化说明：所有查询均为参数化绑定，避免全表扫描的主要手段是上述日期/外键索引；收支记录列表查询以 `LIMIT ?` 约束返回规模（`assetService.records`，默认 200、上限 500）。

## 6. 数据迁移机制

### 6.1 版本标识
以 SQLite 内置的 `PRAGMA user_version` 记录 schema 版本，当前版本为 `4`（`SCHEMA_V1` 对应最初 12 张业务表，`SCHEMA_V2` 新增 `birthdays` 生日表，`SCHEMA_V3` 新增 `moods` 每日心情表，`SCHEMA_V4` 删除 5 张历史表并新增 5 张表，现共 14 张业务表，详见 6.5）。

### 6.2 启动流程
`getDb()` 首次调用（应用主进程初始化）时触发 `migrate(db)`：
1. 读取 `PRAGMA user_version`，得到当前版本号（缺省按 0 处理）。
2. 若版本号小于目标版本，则执行对应版本的建表语句，并回写 `PRAGMA user_version`。
3. 迁移完成后调用 `seedDefaults(db)` 写入种子数据（幂等）。

### 6.3 幂等与升级策略
- 建表语句全部使用 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，重复执行安全。
- 版本号递增执行，`version < N` 的判断保证不会重复应用历史迁移。
- 未来升级（如 V2）应新增 `SCHEMA_V2` 常量并追加 `if (version < 2)` 分支，迁移块内建议用事务包裹，保证「建表/改表 + 版本号更新」原子完成；严禁直接修改已发布版本的建表语句，以免新老库结构不一致。
- 本次日历功能的 V2 升级即按此约定实现：新增 `SCHEMA_V2` 常量并追加 `if (version < 2)` 分支，仅新增 `birthdays` 生日表（`CREATE TABLE IF NOT EXISTS` 幂等建表），老库升级与全新库初始化的结构保持一致。
- 本次「天气 / 每日心情」功能的 V3 升级同样按此约定实现：新增 `SCHEMA_V3` 常量并追加 `if (version < 3)` 分支，仅新增 `moods` 每日心情表（`CREATE TABLE IF NOT EXISTS` 幂等建表），老库升级与全新库初始化的结构保持一致。
- 本次 V4 升级在此基础上引入了**破坏性变更**（删表），与此前「只增不改」的迁移不同，单独说明见 6.5。

### 6.4 伪代码

```text
function migrate(db):
    version = PRAGMA user_version
    if version < 1:
        db.exec(SCHEMA_V1)          # CREATE TABLE IF NOT EXISTS ... x12
        db.exec('PRAGMA user_version = 1')
    if version < 2:
        db.exec(SCHEMA_V2)          # CREATE TABLE IF NOT EXISTS birthdays
        db.exec('PRAGMA user_version = 2')
    if version < 3:
        db.exec(SCHEMA_V3)          # CREATE TABLE IF NOT EXISTS moods
        db.exec('PRAGMA user_version = 3')
    if version < 4:
        db.exec(SCHEMA_V4)          # DROP 5 张历史表 + CREATE 5 张新表（见 6.5）
        db.exec('PRAGMA user_version = 4')
    seedDefaults(db)                # 幂等写入种子数据
```

### 6.5 V4 迁移说明（功能广场改版）

V4 是一次**破坏性迁移**，属产品决策：彻底移除功能广场改版前的 13 项功能（9 个分类学习模块、新闻资讯、工作复盘），连同历史数据一并删除，不可回滚。

- **删除 5 张表**（`DROP TABLE IF EXISTS`，数据随表一并删除）：`modules`、`module_records`、`module_notes`（9 个分类学习模块）、`news`（新闻资讯）、`reviews`（工作复盘）。
- **新增 5 张表**（`CREATE TABLE IF NOT EXISTS`）：`anniversaries`（倒数日与纪念日）、`asset_accounts`（资产平台账户）、`asset_records`（收支记录）、`saving_goals`（攒钱目标，含攒钱计划 / 想买）、`saving_deposits`（攒钱存入明细），字段定义见第 4 章。
- **保留 9 张表不变**：`settings`、`schedules`、`todos`、`habits`、`habit_logs`、`priorities`、`focus_logs`（每日计划页专注计时继续使用）、`birthdays`、`moods`。
- 老库（user_version ≤ 3）升级时依次执行历史迁移后进入 `if (version < 4)` 分支；全新安装依次执行 V1–V4 直接建到 V4（V1 中被删的表会先建后删，最终结构一致）。`DROP TABLE IF EXISTS` 与 `CREATE TABLE IF NOT EXISTS` 均幂等，迁移分支重复进入也安全。
- 迁移后种子数据不再包含 9 个默认学习模块（种子逻辑见第 7 章，仅保留 5 个默认习惯与 `userName`）。
- 由于旧表数据被物理删除，老用户升级前如需留存模块/资讯/复盘数据，应先在旧版本中导出 JSON 备份；备份恢复流程（第 9 章）不再读写已删除的表。

## 7. 种子数据设计

首次启动（或目标表为空）时由 `seedDefaults(db)` 写入，采用「先计数、为 0 才插入」的幂等策略，避免重复写入。

### 7.1 默认习惯（habits，5 条）
按 `sort_order` 依次为：跑步（图标为奔跑者 emoji）、英语学习（书本 emoji）、阅读（书堆 emoji）、多喝水（水滴 emoji）、早起（日出 emoji）。`target` 除「多喝水」为 2 外，其余均为 1；`archived` 默认 0。

### 7.2 默认设置（settings）
若不存在 `key = 'userName'` 的记录，则插入 `('userName', '')`，用户名默认为空串。

侧边栏配置（`key = 'sidebar'`）不写入种子数据：读取时若不存在或格式非法则回退为默认配置（`DEFAULT_SIDEBAR`），首次在「功能广场」中增删功能时再写入。

外观主题（`key = 'theme'`）同样不写入种子数据：读取时若不存在或非合法主题 id 则回退默认主题（`forest`，目录见 `src/shared/themes.ts`），用户首次在设置页切换主题时经 `app:set-theme` 写入；该键位于 settings 表内，随数据备份/恢复一并迁移。

### 7.3 幂等实现

```text
if COUNT(*) FROM habits == 0: 批量 INSERT 5 条默认习惯
if COUNT(*) FROM settings WHERE key='userName' == 0: INSERT ('userName','')
```

说明：V4 之前的种子数据还包含 9 条默认分类模块（写入 `modules` 表）；V4 迁移删除该表后，模块种子一并移除，种子数据仅剩默认习惯与 `userName` 两项。

## 8. 数据完整性约束

### 8.1 主键
- 14 张表中，12 张使用 `INTEGER PRIMARY KEY AUTOINCREMENT` 自增主键（schedules、todos、habits、habit_logs、priorities、focus_logs、birthdays、anniversaries、asset_accounts、asset_records、saving_goals、saving_deposits）。
- `settings` 使用业务字段 `key` 作为 TEXT 主键；`moods` 使用 `date` 作为 TEXT 主键。

### 8.2 唯一约束
- `habit_logs`：`UNIQUE(habit_id, date)`，保证「一个习惯一天一条」打卡记录。

### 8.3 外键与级联
外键约束已通过 `PRAGMA foreign_keys = ON` 在两种驱动上启用（连接建立时设置），因此级联删除真实生效：

| 外键 | 引用 | 行为 |
| --- | --- | --- |
| habit_logs.habit_id | habits(id) | ON DELETE CASCADE |
| asset_records.account_id | asset_accounts(id) | ON DELETE CASCADE |
| saving_deposits.goal_id | saving_goals(id) | ON DELETE CASCADE |

即删除某习惯会一并删除其全部打卡记录；删除某账户会一并删除其全部收支记录；删除某攒钱目标会一并删除其全部存入明细。`schedules`、`todos`、`priorities`、`focus_logs`、`birthdays`、`moods`、`anniversaries` 之间无外键关联，均为独立业务表。重要提示：备份恢复流程中若临时关闭外键（如某些外部工具），须在应用层保证删除顺序（先删子表再删父表），否则可能产生悬挂数据。

### 8.4 默认值与 NOT NULL
- 除 `anniversaries.year` 外（可空，倒数日必填、纪念日留空，由应用层控制），所有业务字段均为 `NOT NULL` 并带默认值（文本默认 `''`，整数默认 `0`，`priority` 默认 `'medium'`，`habits.target` 默认 `1`；V4 新表中 `anniversaries.kind` 默认 `'anniversary'`、`asset_accounts.platform` 默认 `'other'`、`asset_records.kind` 默认 `'expense'`、`asset_records.category` 默认 `'其他'`、`saving_goals.kind` 默认 `'plan'`、`saving_goals.period` 默认 `'monthly'`）。
- 时间戳字段默认 `datetime('now','localtime')`；`asset_accounts.updated_at` 在编辑账户或余额联动时由 SQL 显式改写为当前时间。

### 8.5 应用层约束（无 CHECK 约束）
代码未使用 `CHECK` 约束，以下取值范围由应用层保证，非法值不会被数据库拒绝，需在服务层继续维持：
- `done`、`archived`：仅取 0/1（写入前以三目运算转换）。
- `priority`：仅取 `high` / `medium` / `low`。
- `moods.mood`：语义为 1-5 档，非法值回退为 3。
- `habit_logs.count`：限制在 `[0, target * 3]`。
- `focus_logs.minutes`：取整并钳制为非负。
- `anniversaries.kind`：仅取 `countdown` / `anniversary`（非法值回退 `anniversary`）；`countdown` 时 `year` 必填，`anniversary` 时 `year` 可空（共享层 `normalizeAnniversary` 校验）。
- `asset_accounts.platform`：仅取 12 个平台 key（alipay/wechat/jd/icbc/ccb/abc/boc/cmb/bocom/psbc/cash/other），未知值回退 `other`（`platformOf`）。
- `asset_records.kind`：仅取 `income` / `expense`；`amount` 为正数并保留两位小数。
- `saving_goals.kind`：仅取 `plan` / `wish`；`period`：仅取 `daily` / `weekly` / `monthly` / `yearly` / `none`，`period ≠ 'none'` 时 `per_amount` 应大于 0；已存金额达到 `target` 时由服务层自动将 `done` 置 1。
- 金额字段（`balance`、`amount`、`target`、`per_amount`）统一以「元」为单位（REAL），写入经四舍五入保留两位小数，展示时格式化到分。

## 9. 备份、导出与恢复格式

实现位于 `src/main/services/settings.service.ts`，使用 JSON 文件作为交换格式（Electron 原生保存/选择对话框）。

### 9.1 导出文件格式
导出 payload 结构（`BackupPayload`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| app | string | 固定为 `Workbench`，用于恢复时校验来源 |
| version | string | 应用版本号（`app.getVersion()`） |
| exportedAt | string | 导出时间，ISO 8601 字符串 |
| tables | Record<string, unknown[]> | 各表数据，键为表名，值为该表行数组 |
| settings | Record<string, string> | 预留字段，导出时写入空对象 `{}` |

默认文件名为 `Workbench-备份-YYYY-MM-DD.json`，内容为格式化（缩进 2 空格）的 UTF-8 JSON。

### 9.2 包含范围
`BACKUP_TABLES` 定义导出表与列（按外键依赖顺序排列），覆盖全部 14 张表：habits、habit_logs、schedules、todos、priorities、focus_logs、birthdays、moods、anniversaries、asset_accounts、asset_records、saving_goals、saving_deposits、settings。每表按显式列名 `SELECT` 导出（如 `asset_records` 导出 id、account_id、kind、category、amount、date、note、created_at）。

版本兼容说明：V4 起 `BACKUP_TABLES` 删除了 modules、module_records、module_notes、news、reviews 五张旧表，新增 anniversaries、asset_accounts、asset_records、saving_goals、saving_deposits。旧版本导出的备份 JSON 中，已删除表的数据在恢复时会被忽略（恢复仅按当前 `BACKUP_TABLES` 逐表读取 `tables[表名]`，多余键不处理），其余表可正常迁移到新版本。

说明：数据存储位置配置（`userData/storage.json`，见 2.2）属于环境级目录配置而非业务数据，不包含在 JSON 备份中；备份与恢复始终作用于当前正在使用的数据库（无论其位于默认目录还是应用内更改后的自定义目录）。

### 9.3 恢复流程与覆盖策略
1. 读取并解析 JSON，校验 `app === 'Workbench'` 且存在 `tables`，否则抛出「备份文件格式不正确」。
2. 开启事务 `BEGIN`。
3. 按 `BACKUP_TABLES` 的逆序（先子表后父表）执行 `DELETE FROM <表>` 清空业务表；`settings` 表不参与清空（保留现有设置）。
4. 按 `BACKUP_TABLES` 顺序对每张表执行 `INSERT OR REPLACE`，空行数组跳过；settings 亦会被写入或覆盖。
5. 成功后 `COMMIT`；任一步骤异常则 `ROLLBACK` 并向上抛出，保证不产生半成品数据。
6. 返回备份文件路径作为结果。

策略要点：恢复为**整表覆盖**语义（先清空再写入），非合并；`settings.userName` 因不清空且 `INSERT OR REPLACE`，最终以备份内容为准。

## 10. 典型查询与统计口径

| 统计项 | 口径 | 实现位置 |
| --- | --- | --- |
| 单日任务完成数/总数 | schedules + todos + priorities 三表在指定 `date` 的行数及 `done = 1` 行数之和 | `statsService.taskCount` |
| 单日习惯完成率（首页口径） | 未归档习惯中，`COALESCE(count,0) >= target` 的习惯数 / 习惯总数 | `statsService.habitCompletionCount` |
| 单日习惯达成度（趋势口径） | 目标总和为各习惯 `target`（`<=0` 按 1）之和；已完成为各习惯 `min(count, target)` 之和 | `statsService.habitCount` |
| 今日进度百分比 | `round((任务完成 + 习惯完成) / (任务总数 + 习惯总数) * 100)`，无项时 0 | `computeProgress`（逻辑层），`statsService.day` 调用 |
| 今日状态文案 | 按进度分档：`>=80` 状态极佳、`>=50` 保持专注、`>=20` 继续加油、否则开始行动；无项时「等待计划」 | `statusLabel`（逻辑层） |
| 单日专注时长 | `SUM(minutes) WHERE date = ?` | `statsService.focusMinutes`、`focusService.todayMinutes` |
| 近 7 天趋势 | 对最近 n 天（含今天）逐日输出任务完成/总数、习惯次数/目标、专注分钟 | `statsService.trend`（配合 `recentDates`） |
| 累计完成任务数 | schedules + todos + priorities 全表 `done = 1` 行数之和 | `statsService.overview` |
| 累计打卡次数 | `SUM(count) FROM habit_logs` | `statsService.overview`（`habitService.totalCheckCount` 同口径） |
| 当前连续打卡天数 | 取 `habit_logs` 中 `count > 0` 的去重日期集合，从今天向前回溯连续命中天数 | `habitStreak`（逻辑层），`statsService.overview` 调用 |
| 心情连续打卡天数 | 取 `moods` 的日期集合（首页加载今天往前 366 天记录），从今天向前回溯连续命中天数；今天未记录时为 0 | `moodStreak`（共享层 `moods.ts`），`HomeView.vue` 调用 |
| 累计专注时长 | `SUM(minutes) FROM focus_logs` | `statsService.overview` |
| 总资产余额 | `SUM(balance) FROM asset_accounts`（含账户数） | `assetService.summary` |
| 区间收支合计 | `SUM(amount) WHERE kind = ? AND date BETWEEN ? AND ?`（收入/支出分别聚合） | `assetService.summary` |
| 总资产趋势 | 当前总余额减去「今天之后」全部记录的净额（`SUM(income) - SUM(expense) WHERE date > today`），再自今天向前按窗口内每日收支净额逐日回推 | `assetService.trend` |
| 收支分类分布 | `SUM(amount)`、`COUNT(id)` 按 `category` 分组（按 kind 区分收入/支出，可按月过滤，倒序） | `assetService.categoryStats` |
| 攒钱目标已存金额 | 关联子查询 `COALESCE((SELECT SUM(amount) FROM saving_deposits WHERE goal_id = g.id), 0)`，已存达标时 `done` 自动置 1 | `savingsService.list` |
| 习惯连续打卡（单习惯） | 该习惯 `count > 0` 的全部日期（倒序） | `habitService.checkedDates` |

说明：「今日完成率」在首页/每日计划页采用**已达标习惯数 / 习惯总数**口径；在近 7 天趋势中习惯维度采用**打卡次数 / 目标次数**口径，两者分别由 `habitCompletionCount` 与 `habitCount` 实现，注意区分。

## 11. 容量与性能估算

### 11.1 数据增长量级
- 单用户、日频写入。以典型使用强度估算：每日新增 5-20 条任务、5-10 条习惯打卡、1-5 条专注记录、0-5 条收支记录、0-2 条存入明细，年增行数约 1 万级。
- 单行数据以文本为主（标题、备注），单库文件通常在数 MB 级别，数年使用也远未触及 SQLite 容量瓶颈。

### 11.2 WAL 影响
- WAL 模式下写操作追加到 `-wal` 文件，读操作不阻塞写，写入无需频繁 fsync（`synchronous = NORMAL`），显著提升响应速度。
- WAL 文件会随写入增长，读事务结束后由检查点自动回收；应用退出时执行 `wal_checkpoint(TRUNCATE)` 归并并收缩，避免日志无限膨胀。
- 若异常退出遗留较大 WAL，下次启动读取时会自动恢复；数据目录备份时建议在应用关闭后进行，或以 `workbench.db` 为准（此时 WAL 已 checkpoint）。

### 11.3 维护建议
- 频繁删除（如批量清理习惯打卡、收支记录）会导致文件内部空闲页增多，可定期执行 `VACUUM` 回收空间（建议在应用关闭状态进行）。V4 迁移的 5 次 `DROP TABLE` 同样会留下空闲页，老库升级后可择机 `VACUUM` 一次。
- 收支记录列表查询已用 `LIMIT ?`（上限 500）约束；若未来数据量增长，可为 `asset_records.date` 补充复合索引（如 `(account_id, date)`）以优化「账户 + 月份」组合过滤。
- 单文件数据库便于整体备份，无需分库分表。

## 12. 附录

### 12.1 字段命名规范
- 表名、字段名统一小写 `snake_case`（如 `account_id`、`sort_order`、`created_at`）。
- TS 侧映射为 `camelCase`（如 `accountId`、`sortOrder`、`createdAt`），映射在各 service 的 `mapXxx` 函数中完成。
- 布尔语义字段命名用过去分词或状态词（`done`、`archived`）。
- 时间戳统一 `created_at` / `updated_at`。

### 12.2 时间与日期存储约定
- 日期字段（`date`）统一为 `YYYY-MM-DD` 字符串（本地时区）。
- 时间字段（`time`、`start_time`、`end_time`）统一为 `HH:mm` 字符串，可为空串表示未设置。
- 时间戳字段（`created_at`、`updated_at`）为 `datetime('now','localtime')` 生成的 `YYYY-MM-DD HH:mm:ss` 本地时间字符串。
- 文本日期便于按字典序比较与日期区间查询，无需在 SQL 中做类型转换。

### 12.3 布尔存储约定
- 布尔值统一使用 `INTEGER` 的 0/1 存储（`done`、`archived`）。
- 读取时通过 `Number(value) === 1` 转为 TS `boolean`；写入时以 `cond ? 1 : 0` 转换。

### 12.4 其他约定
- 主键自增列显式声明 `AUTOINCREMENT`，保证 id 单调不复用。
- 文本字段一律 `NOT NULL + DEFAULT ''`，避免 NULL 参与比较带来的语义歧义。
- 所有 SQL 均参数化绑定，杜绝注入。
- 单元测试 `tests/unit/storage.test.ts` 使用 `node:sqlite`（内存库）覆盖存储层 21 个用例，验证建表、读写与统计口径。
