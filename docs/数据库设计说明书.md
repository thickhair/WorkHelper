## 1. 文档信息

| 文档类型 | 数据库设计说明书 | 编写日期 | 2026-10-08 |

本文档描述 WorkHelper 本地数据存储的选型、表结构、索引、迁移、种子数据、完整性约束、备份恢复与统计查询口径。所有表名、字段名、类型、约束与索引均与代码实现严格一致，可直接作为数据层开发与维护依据。相关实现位于 `src/main/db/database.ts`、`src/main/db/sqlite-adapter.ts`、`src/main/services/*.service.ts`、`src/shared/types.ts`。

## 2. 存储方案概述

### 2.1 选型理由
- 单机离线应用，数据仅供本机单用户使用，无需网络与并发写服务，SQLite 零配置、单文件、免安装，天然契合。
- 支持事务、外键、索引与 WAL 增量写，足以支撑日频次、低并发的工作台场景。
- 数据文件随应用目录即可整体拷贝，便于备份与便携迁移。

### 2.2 文件位置
- 默认目录：`app.getPath('userData')/data`，Windows 下即 `%APPDATA%/WorkHelper/data`。
- 数据库文件：`workhelper.db`；WAL 模式启用后同目录下还会出现 `workhelper.db-wal`（预写日志）与 `workhelper.db-shm`（共享内存索引）两个临时文件。
- 可通过环境变量 `WORKHELPER_DATA_DIR` 重定向 `userData` 根目录（便携模式 / 开发调试），见 `src/main/index.ts`。

### 2.3 驱动适配策略
`src/main/db/sqlite-adapter.ts` 通过统一接口屏蔽底层驱动差异：
- 优先加载 `better-sqlite3`（13.0.3，性能最佳，随应用打包）；加载失败（如原生模块 ABI 不匹配）时自动回退到 Node 内置 `node:sqlite` 的 `DatabaseSync`。
- 对外统一暴露三个接口：`SqliteDatabase`（exec / prepare / close）、`SqliteStatement`（run / get / all）、`SqliteRunResult`（changes / lastInsertRowid）。业务层仅依赖该接口，便于替换驱动与单元测试。
- 当前实际驱动名可通过设置页「关于信息」查看（`settingsService.driver()`）。

### 2.4 连接参数
打开数据库后立即执行以下 PRAGMA（两种驱动一致）：

| PRAGMA | 取值 | 作用 |
| --- | --- | --- |
| journal_mode | WAL | 预写日志，提升读写并发与写入性能 |
| synchronous | NORMAL | 兼顾安全与性能的持久化级别 |
| foreign_keys | ON | 启用外键约束，级联删除生效 |

应用退出（`closeDb`）前执行 `PRAGMA wal_checkpoint(TRUNCATE)`，将 WAL 内容合并进主库并收缩日志文件。

## 3. 数据库 ER 关系概览

```text
modules (key PK)
   |-- 1:N --> module_records (module_key FK, ON DELETE CASCADE)
   |-- 1:N --> module_notes   (module_key FK, ON DELETE CASCADE)

habits (id PK)
   |-- 1:N --> habit_logs (habit_id FK, ON DELETE CASCADE, UNIQUE(habit_id,date))

settings      独立键值表（key PK）
schedules     独立（按 date 查询）
todos         独立（按 date 查询）
priorities    独立（按 date 查询）
news          独立（本地资讯条目）
reviews       独立（date UNIQUE，每天一篇）
focus_logs    独立（按 date 查询）
```

关系说明：
- `habits` 与 `habit_logs` 为一对多（1:N），每个习惯每天至多一条打卡记录，由 `UNIQUE(habit_id, date)` 保证；删除习惯级联删除其打卡记录。
- `modules` 与 `module_records`、`module_notes` 均为一对多，模块以字符串业务主键 `key` 关联（非自增 id）；删除模块级联删除其记录与笔记。
- `schedules`、`todos`、`priorities` 无显式外键，通过 `date` 归集到「某一天」，是首页与每日计划页统计口径的数据来源。
- `focus_logs` 记录专注计时明细，按 `date` 汇总；`reviews` 以 `date` 唯一约束实现「每天一篇」；`settings` 为全局键值配置。

## 4. 表结构详细设计

约定：SQLite 为动态类型，索引与约束以声明类型为准。布尔语义统一用 `INTEGER` 的 0/1 表示，TS 侧映射为 `boolean`。时间戳字段默认值均为 `datetime('now','localtime')`，格式为 `YYYY-MM-DD HH:mm:ss`。

### 4.1 settings（应用设置）
用途：存储全局配置的键值对。TS 映射：无独立接口，经 `settingsService` 读写，主要为 `AppSettings.userName`、侧边栏配置 `AppSettings.sidebar` 与外观主题 `AppSettings.theme`。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| key | TEXT | PRIMARY KEY | 无 | 配置项名称，如 `userName`、`sidebar`、`theme` |
| value | TEXT | NOT NULL | 无 | 配置项取值（统一以字符串存储；`sidebar` 为功能 id 数组的 JSON 字符串，`theme` 为主题 id 字符串） |

主键：`key`。外键：无。索引：主键隐式唯一索引。

## 5. 索引与查询优化

显式索引共 7 个，均服务于「按日期过滤」或「按模块聚合」的查询；其余为各表主键与唯一约束的隐式索引。

| 索引名 | 表 | 列 | 服务的查询场景（对应服务方法） |
| --- | --- | --- | --- |
| idx_schedules_date | schedules | date | `scheduleService.list`、`statsService.taskCount`（`WHERE date = ?`） |
| idx_todos_date | todos | date | `todoService.list`、`statsService.taskCount`（`WHERE date = ?`） |
| idx_priorities_date | priorities | date | `priorityService.list`、`statsService.taskCount`（`WHERE date = ?`） |
| idx_habit_logs_date | habit_logs | date | `habitService.countsByDate`（`WHERE date = ?`） |
| idx_module_records_key | module_records | module_key | `moduleService.records`、`moduleService.summary`（`WHERE module_key = ?`） |
| idx_module_notes_key | module_notes | module_key | `moduleService.notes`（`WHERE module_key = ?`） |
| idx_focus_logs_date | focus_logs | date | `focusService.todayMinutes`、`statsService.focusMinutes`（`WHERE date = ?`） |

其他可利用的隐式索引：
- `habit_logs` 的 `UNIQUE(habit_id, date)` 复合唯一索引，可用于 `WHERE habit_id = ?`（`habitService.checkedDates`）及 `habit_id + date` 等值定位。
- `reviews.date` 的 UNIQUE 索引，服务 `reviewService.get(date)`。
- `statsService.habitCount` / `habitCompletionCount` 以 `habits` 为主表 `LEFT JOIN habit_logs ON habit_id = ? AND date = ?`，习惯表数据量小，主要开销在 habit_logs 的复合唯一索引命中。

优化说明：所有查询均为参数化绑定，避免全表扫描的主要手段是上述日期/模块索引；列表查询普遍附加 `LIMIT 500`（`news`、`module_records`、`reviews`）以约束返回规模。

## 6. 数据迁移机制

### 6.1 版本标识
以 SQLite 内置的 `PRAGMA user_version` 记录 schema 版本，当前版本为 `1`（常量 `SCHEMA_V1` 对应 12 张业务表）。

### 6.2 启动流程
`getDb()` 首次调用（应用主进程初始化）时触发 `migrate(db)`：
1. 读取 `PRAGMA user_version`，得到当前版本号（缺省按 0 处理）。
2. 若版本号小于目标版本，则执行对应版本的建表语句，并回写 `PRAGMA user_version`。
3. 迁移完成后调用 `seedDefaults(db)` 写入种子数据（幂等）。

### 6.3 幂等与升级策略
- 建表语句全部使用 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，重复执行安全。
- 版本号递增执行，`version < N` 的判断保证不会重复应用历史迁移。
- 未来升级（如 V2）应新增 `SCHEMA_V2` 常量并追加 `if (version < 2)` 分支，迁移块内建议用事务包裹，保证「建表/改表 + 版本号更新」原子完成；严禁直接修改已发布版本的建表语句，以免新老库结构不一致。

### 6.4 伪代码

```text
function migrate(db):
    version = PRAGMA user_version
    if version < 1:
        db.exec(SCHEMA_V1)          # CREATE TABLE IF NOT EXISTS ... x12
        db.exec('PRAGMA user_version = 1')
    # if version < 2: db.exec(SCHEMA_V2); db.exec('PRAGMA user_version = 2')
    seedDefaults(db)                # 幂等写入种子数据
```

## 7. 种子数据设计

首次启动（或目标表为空）时由 `seedDefaults(db)` 写入，采用「先计数、为 0 才插入」的幂等策略，避免重复写入。

| creation | 爆款二创 | 每周拆解 3 个爆款，产出二次创作 |
| ai | AI学习 | 跟进 AI 前沿工具，每周实践 1 个新玩法 |

每个模块的 icon 为对应主题 emoji（运动、书本、场记板、耳机、对话、书堆、连衣裙、火焰、机器人）。

### 7.3 默认设置（settings）
若不存在 `key = 'userName'` 的记录，则插入 `('userName', '')`，用户名默认为空串。

侧边栏配置（`key = 'sidebar'`）不写入种子数据：读取时若不存在或格式非法则回退为默认配置（`DEFAULT_SIDEBAR`），首次在「功能广场」中增删功能时再写入。

外观主题（`key = 'theme'`）同样不写入种子数据：读取时若不存在或非合法主题 id 则回退默认主题（`forest`，目录见 `src/shared/themes.ts`），用户首次在设置页切换主题时经 `app:set-theme` 写入；该键位于 settings 表内，随数据备份/恢复一并迁移。

### 7.4 幂等实现

```text
if COUNT(*) FROM habits == 0: 批量 INSERT 5 条默认习惯
if COUNT(*) FROM modules == 0: 批量 INSERT 9 条默认模块
if COUNT(*) FROM settings WHERE key='userName' == 0: INSERT ('userName','')
```

## 8. 数据完整性约束

### 8.1 主键
- 12 张表中，10 张使用 `INTEGER PRIMARY KEY AUTOINCREMENT` 自增主键（schedules、todos、habits、habit_logs、priorities、module_records、module_notes、news、reviews、focus_logs）。
- `settings` 与 `modules` 使用业务字段作为 TEXT 主键（`key`）。

### 8.2 唯一约束
- `habit_logs`：`UNIQUE(habit_id, date)`，保证「一个习惯一天一条」打卡记录。
- `reviews`：`date` UNIQUE，保证「每天一篇」复盘。

### 8.3 外键与级联
外键约束已通过 `PRAGMA foreign_keys = ON` 在两种驱动上启用（连接建立时设置），因此级联删除真实生效：

| 外键 | 引用 | 行为 |
| --- | --- | --- |
| habit_logs.habit_id | habits(id) | ON DELETE CASCADE |
| module_records.module_key | modules(key) | ON DELETE CASCADE |
| module_notes.module_key | modules(key) | ON DELETE CASCADE |

即删除某习惯会一并删除其全部打卡记录；删除某模块会一并删除其全部投入记录与笔记。`schedules`、`todos`、`priorities`、`news`、`reviews`、`focus_logs` 之间无外键关联，均为独立业务表。重要提示：备份恢复流程中若临时关闭外键（如某些外部工具），须在应用层保证删除顺序（先删子表再删父表），否则可能产生悬挂数据。

### 8.4 默认值与 NOT NULL
- 所有业务字段均为 `NOT NULL` 并带默认值（文本默认 `''`，整数默认 `0`，`priority` 默认 `'medium'`，`mood` 默认 `3`，`target` 默认 `1`）。
- 时间戳字段默认 `datetime('now','localtime')`；`module_notes.updated_at` 与 `reviews.updated_at` 在编辑时由 SQL 显式改写为当前时间。

### 8.5 应用层约束（无 CHECK 约束）
代码未使用 `CHECK` 约束，以下取值范围由应用层保证，非法值不会被数据库拒绝，需在服务层继续维持：
- `done`、`archived`、`favorite`：仅取 0/1（写入前以三目运算转换）。
- `priority`：仅取 `high` / `medium` / `low`。
- `mood`：语义为 1-5 档，默认 3。
- `habit_logs.count`：限制在 `[0, target * 3]`。
- `module_records.duration`、`focus_logs.minutes`：取整并钳制为非负。

## 9. 备份、导出与恢复格式

实现位于 `src/main/services/settings.service.ts`，使用 JSON 文件作为交换格式（Electron 原生保存/选择对话框）。

### 9.1 导出文件格式
导出 payload 结构（`BackupPayload`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| app | string | 固定为 `WorkHelper`，用于恢复时校验来源 |
| version | string | 应用版本号（`app.getVersion()`） |
| exportedAt | string | 导出时间，ISO 8601 字符串 |
| tables | Record<string, unknown[]> | 各表数据，键为表名，值为该表行数组 |
| settings | Record<string, string> | 预留字段，导出时写入空对象 `{}` |

默认文件名为 `WorkHelper-备份-YYYY-MM-DD.json`，内容为格式化（缩进 2 空格）的 UTF-8 JSON。

### 9.2 包含范围
`BACKUP_TABLES` 定义导出表与列（按外键依赖顺序排列），覆盖全部 12 张表：modules、habits、habit_logs、schedules、todos、priorities、module_records、module_notes、news、reviews、focus_logs、settings。每表按显式列名 `SELECT` 导出（如 `module_records` 导出 id、module_key、date、title、duration、note、created_at）。

### 9.3 恢复流程与覆盖策略
1. 读取并解析 JSON，校验 `app === 'WorkHelper'` 且存在 `tables`，否则抛出「备份文件格式不正确」。
2. 开启事务 `BEGIN`。
3. 按 `BACKUP_TABLES` 的逆序（先子表后父表）执行 `DELETE FROM <表>` 清空业务表；`settings` 表不参与清空（保留现有设置）。
4. 按 `BACKUP_TABLES` 顺序对每张表执行 `INSERT OR REPLACE`，空行数组跳过；settings 亦会被写入或覆盖。
5. 成功后 `COMMIT`；任一步骤异常则 `ROLLBACK` 并向上抛出，保证不产生半成品数据。
6. 返回备份文件路径作为结果。

策略要点：恢复为**整表覆盖**语义（先清空再写入），非合并；`settings.userName` 因不清空且 `INSERT OR REPLACE`，最终以备份内容为准。

## 10. 典型查询与统计口径

| 统计项 | 口径 | 实现位置 |
| --- | --- | --- |
| 单日任务完成数/总数 | schedules + todos + priorities 三表在指定 `date` 的行数及 `done = 1` 行数之和 | `statsService.taskCount` |
| 单日习惯完成率（首页口径） | 未归档习惯中，`COALESCE(count,0) >= target` 的习惯数 / 习惯总数 | `statsService.habitCompletionCount` |
| 单日习惯达成度（趋势口径） | 目标总和为各习惯 `target`（`<=0` 按 1）之和；已完成为各习惯 `min(count, target)` 之和 | `statsService.habitCount` |
| 今日进度百分比 | `round((任务完成 + 习惯完成) / (任务总数 + 习惯总数) * 100)`，无项时 0 | `computeProgress`（逻辑层），`statsService.day` 调用 |
| 今日状态文案 | 按进度分档：`>=80` 状态极佳、`>=50` 保持专注、`>=20` 继续加油、否则开始行动；无项时「等待计划」 | `statusLabel`（逻辑层） |
| 单日专注时长 | `SUM(minutes) WHERE date = ?` | `statsService.focusMinutes`、`focusService.todayMinutes` |
| 近 7 天趋势 | 对最近 n 天（含今天）逐日输出任务完成/总数、习惯次数/目标、专注分钟 | `statsService.trend`（配合 `recentDates`） |
| 累计完成任务数 | schedules + todos + priorities 全表 `done = 1` 行数之和 | `statsService.overview` |
| 累计打卡次数 | `SUM(count) FROM habit_logs` | `statsService.overview`（`habitService.totalCheckCount` 同口径） |
| 当前连续打卡天数 | 取 `habit_logs` 中 `count > 0` 的去重日期集合，从今天向前回溯连续命中天数 | `habitStreak`（逻辑层），`statsService.overview` 调用 |
| 累计专注时长 | `SUM(minutes) FROM focus_logs` | `statsService.overview` |
| 模块投入排行 | `modules LEFT JOIN module_records` 按 `module_key` 分组，汇总 `SUM(duration)` 与 `COUNT(id)`，按时长倒序 | `moduleService.trend` |
| 模块累计统计 | 单模块的记录次数、时长合计、最近记录日期（`MAX(date)`） | `moduleService.summary` |
| 习惯连续打卡（单习惯） | 该习惯 `count > 0` 的全部日期（倒序） | `habitService.checkedDates` |

说明：「今日完成率」在首页/每日计划页采用**已达标习惯数 / 习惯总数**口径；在近 7 天趋势中习惯维度采用**打卡次数 / 目标次数**口径，两者分别由 `habitCompletionCount` 与 `habitCount` 实现，注意区分。

## 11. 容量与性能估算

### 11.1 数据增长量级
- 单用户、日频写入。以典型使用强度估算：每日新增 5-20 条任务、5-10 条习惯打卡、1-5 条专注记录、0-3 条模块记录、0-1 篇复盘，年增行数约 1 万级。
- 单行数据以文本为主（标题、备注），单库文件通常在数 MB 级别，数年使用也远未触及 SQLite 容量瓶颈。

### 11.2 WAL 影响
- WAL 模式下写操作追加到 `-wal` 文件，读操作不阻塞写，写入无需频繁 fsync（`synchronous = NORMAL`），显著提升响应速度。
- WAL 文件会随写入增长，读事务结束后由检查点自动回收；应用退出时执行 `wal_checkpoint(TRUNCATE)` 归并并收缩，避免日志无限膨胀。
- 若异常退出遗留较大 WAL，下次启动读取时会自动恢复；数据目录备份时建议在应用关闭后进行，或以 `workhelper.db` 为准（此时 WAL 已 checkpoint）。

### 11.3 维护建议
- 频繁删除（如批量清理复盘、习惯打卡）会导致文件内部空闲页增多，可定期执行 `VACUUM` 回收空间（建议在应用关闭状态进行）。
- 长列表查询已用 `LIMIT 500` 约束；若未来数据量增长，可为 `news.created_at`、`reviews.date`、`module_records.date` 补充索引以优化排序与分页。
- 单文件数据库便于整体备份，无需分库分表。

## 12. 附录

### 12.1 字段命名规范
- 表名、字段名统一小写 `snake_case`（如 `module_key`、`sort_order`、`created_at`）。
- TS 侧映射为 `camelCase`（如 `moduleKey`、`sortOrder`、`createdAt`），映射在各 service 的 `mapXxx` 函数中完成。
- 布尔语义字段命名用过去分词或状态词（`done`、`archived`、`favorite`）。
- 时间戳统一 `created_at` / `updated_at`。

### 12.2 时间与日期存储约定
- 日期字段（`date`）统一为 `YYYY-MM-DD` 字符串（本地时区）。
- 时间字段（`time`、`start_time`、`end_time`）统一为 `HH:mm` 字符串，可为空串表示未设置。
- 时间戳字段（`created_at`、`updated_at`）为 `datetime('now','localtime')` 生成的 `YYYY-MM-DD HH:mm:ss` 本地时间字符串。
- 文本日期便于按字典序比较与日期区间查询，无需在 SQL 中做类型转换。

### 12.3 布尔存储约定
- 布尔值统一使用 `INTEGER` 的 0/1 存储（`done`、`archived`、`favorite`）。
- 读取时通过 `Number(value) === 1` 转为 TS `boolean`；写入时以 `cond ? 1 : 0` 转换。

### 12.4 其他约定
- 主键自增列显式声明 `AUTOINCREMENT`，保证 id 单调不复用。
- 文本字段一律 `NOT NULL + DEFAULT ''`，避免 NULL 参与比较带来的语义歧义。
- 所有 SQL 均参数化绑定，杜绝注入。
- 单元测试 `tests/unit/storage.test.ts` 使用 `node:sqlite`（内存库）覆盖存储层 19 个用例，验证建表、读写与统计口径。
